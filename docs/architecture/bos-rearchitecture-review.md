## 1. Verdict

### The precise KERNEL spec

The kernel is **DATA + four thin code contracts**. Nothing vendor-specific. Membership, exhaustively:

**Code (the syscall table — `kernel/runtime/`):**
1. `request(driver_id, method, path|tool, body) -> result | ApprovalPending` — transport-neutral. Parameterized by `base_url + key_resolver + secret_pattern + transport`. Carries the 202/approval + idempotency contract. **A driver implements this by supplying those four params; it never edits kernel code.**
2. `journal(event)` — append-only write log. Captures key-path writes directly; MCP-path writes call `journal_mcp_write(tool, args_summary)` (a one-liner apps include).
3. `preflight(driver_id) -> connected? + remediation` — reads the registry, branches on driver `type`, runs one connection check. Replaces the per-skill inline check currently hand-coded in `skills/sync-from-xero/fetch.py`.
4. `get_profile()/update_profile()` + `get_progress()/update_progress()` — read/write the profile and the progress ledger. **Schema only; the kernel never decides what to ask.**

**Data (no code):**
- The **generated registry** (`registry.json`) — single source of truth for capability/activation.
- The **profile template** + **progress ledger schema**.
- The **safeguards contract** (offline kill-switch, redaction patterns, approval-queue semantics).

**Explicitly NOT in the kernel:** the onboarding/grill engine, the drift checker, the nudge logic, the topic classifier. These are **apps** (skills) that read/write kernel data. Test: *across the next 10 onboarding-copy iterations, does any `kernel/` file change?* If yes, the boundary is wrong.

### The contract between kernel, drivers, apps, registry

```
APP (skill)  --declares-->  manifest frontmatter (function_slot, requires_driver,
                            requires_credential, uses_tools, unlocks, data_path,
                            status, reads_for_profile)
APP  --calls-->  kernel.request() + its own declared tools  (never another driver directly)
DRIVER  --supplies-->  base_url + key_resolver + secret_pattern + transport + type
                       + its own path/override table (PATH_OVERRIDES lives HERE, not kernel)
DRIVER  --declared in-->  drivers/<id>/manifest.json (+ connect tutorial, DATA only)
GENERATOR  --reads all manifests-->  emits registry.json (capability projection)
                                  +  profile-source map (reads_for_profile, onboarding-only)
KERNEL + ONBOARDING + "what can you do"  --read-->  registry.json  (never a hand-kept list)
LINT (extended lint-skill.py)  --FAILS CI on-->  unknown manifest keys, undeclared tool
                               references, vendor literals in kernel/, orphan slots,
                               key-path writes not tagged, resolve_path violations
```

**Two enforced properties that make "swappable" real (not hoped):**
- `uses_tools:` is a lintable field. `lint-skill.py` FAILS if a SKILL.md body references an `mcp__*` tool not declared in its manifest, **or** references a CRM-driver tool while claiming a swappable non-CRM slot. CRM apps naming TrustPager tools freely is the **labelled exception** (per decision 1, per the anti-drift doctrine).
- The generator emits an **activation graph** and CI FAILS if any app's `requires_driver` names a slot no driver fills (orphan app → permanently dark) or any driver fills an unknown slot.

### How a skill reads the registry/driver manifests at runtime — grounded in what the loader allows

**Verified loader reality:** `plugin.json` (read in full) declares only `name/version/description/author/homepage/keywords` — **no component-path manifest.** The Claude Code loader auto-discovers `commands/`, `skills/`, `agents/` at the plugin root by fixed convention. `CLAUDE_PLUGIN_ROOT` is referenced **nowhere** in the repo (grep: zero hits). No hooks exist. Therefore:

- **`kernel/` and `drivers/` are DATA-ONLY directories** — manifests, profile template, connect tutorials, generated `registry.json`. They are read at runtime via plain `Read`/`Glob`, exactly as 40 skills already read `knowledge/` today. They are **never** loaded as skills.
- **Kernel BEHAVIOUR that must trigger ships as real `skills/` entries** tagged `kernel: true` in frontmatter (a tag the generator reads — *not* a loader feature). Concretely: `skills/whats-possible/` (reads registry → "what can you do right now?"), `skills/connect-a-tool/` (runs preflight + connect tutorial), `skills/start-here/` (the onboarding engine).
- A skill reads the registry by: `Read(${plugin_root}/kernel/registry.json)` where `${plugin_root}` is resolved via `CLAUDE_PLUGIN_ROOT` (adopt it now — it is the documented anchor and shrinks the dual-install seam to one branch). The registry is shipped **inside the plugin like a lockfile**, regenerated and diff-checked in CI, so the kernel always reads a registry co-located with the skills it describes.

This keeps the kernel/driver/app taxonomy **purely logical** (decision 2's "internal only"), satisfies the loader, and needs zero new platform features for v1.

- The 202 approval queue is modelled as a first-class return value, not an exception (ApprovalPending, trustpager_api.py:102-135), and safeguards.md §1 explicitly forbids routing around it ('Never try to route around an approval gate'). This is the single best safety primitive in the repo and generalises cleanly to any driver that can issue outward-facing writes.
- Defence-in-depth on the journal: `_redact()` strips key tokens from every journal line and error string before disk (trustpager_api.py:86-93, 363-372), library errors reference only the prefix, config.py masks the stored key. Even though a write body should never carry a key, the redaction assumes it might — correct paranoia.
- resolve_path() + the cached public catalog (trustpager_api.py:619-800) decouple skills from hardcoded paths, and lint-skill.py enforces 'no api_get without resolve_path' (lint-skill.py:118-120). This is exactly the 'data not code' contract the schematic wants to generalise — the pattern is already proven for the CRM driver.

**Risks:**
- [HIGH] **Two parallel credential surfaces exist and the schematic never names the split — this is the load-bearing security fact** — Writes/sends run through the KEYLESS MCP connection (send-email/SKILL.md:17,64 wrap mcp__trustpager__send_email; 17 skills issue MCP writes), while fetch.py read fan-out AND some writes run through a PASTED tp_live_ key in ~/.claude/bos.json (trustpager_api.py:138-165, setup.py:116-133; outstanding-invoices/fetch.py:83,123 calls api_post via the key). Nothing in README/INSTALL/safeguards explains why both exist or which to trust.

Add a `data_path: mcp|key` field to the app manifest so the registry shows, per app, which surface it uses. Forbid key-path writes in lint (extend lint-skill.py: a fetch.py that calls api_post/api_patch/idempotent_post should FAIL unless explicitly tagged write_via_key) — today only outstanding-invoices does it and it should be the documented exception, not silent.

README.md:175 and safeguards.md §3 promise 'every write lands in ~/.claude/bos-journal' — yet the MAJORITY of real writes (every send_email, update_opportunity, create_*, reply_to_email driven from SKILL.md prose) bypass it entirely. This is a churned-trust hazard for a paid Skool community: the marketed safety rail has a hole exactly where most writes happen.  
  → *Fix:* Decide the journal's source of truth. - [MEDIUM] **bos.json stores a long-lived plaintext key with no file-permission hardening** — setup.py:116-133 writes the key to ~/.claude/bos.json with default umask — no chmod 0o600 anywhere (confirmed across setup.py/config.py). The key is also long-lived: nothing in the flow scopes it, expires it, or distinguishes a read-only key from a full-access one, yet get_api_key() will happily use whatever is pasted. The schematic's 'key lands in a .env file, NEVER pasted in chat' framing addresses the chat-optics but not the at-rest exposure, which is the larger real risk as the user base scales.  
  → *Fix:* chmod 0o600 bos.json (and any per-driver .env) on write, cross-platform best-effort. In setup.py, when offering to reuse a detected key, prefer guiding the user to mint a READ-ONLY key for the Python path (the fan-out only reads) and reserve full scope for the MCP connection. Document the at-rest model in TESTING.md's sibling (a SECURITY.md): where keys live, what scope each surface needs, how to rotate.
- [MEDIUM] **The per-driver-secret premise the schematic worries about may be largely false — risk of over-building the .env fallback** — The mandate frames drivers as 'each with its own secrets + scopes' and asks where the security story cracks per-driver. - [MEDIUM] **Keyless-Python rule and offline guard need to be re-pinned as the lint contract survives the refactor** — Today three things keep the key out of code: the BOS_OFFLINE guard, lint-skill.py's hardcoded-key check (lint-skill.py:113), and check-no-secrets.py. - [LOW] **Connect-on-demand multiplies OAuth/secret surfaces with no central scope/consent ledger** — The schematic's 'preflight: have my driver? if not, run the connect tutorial' will, at driver #10-20, mean a non-technical owner has authorised a sprawl of MCP connections and possibly a few .env keys, with no single place that answers 'what is connected, with what scope, and what can act on my behalf right now?'. **Optimizations:**
- Reframe the data-access preference order to match reality: it isn't a linear 'MCP > CLI > key' fallback per tool — it's a role split. # Appendix B — Red-team judgment

**Verdict:** "SOUND DIRECTION, WRONG SEQUENCING — proceed, but re-order the work and demote three over-builds. The microkernel instinct is right and largely already true (Claude's trigger-matching IS the router; resolve_path + the cached catalog + lint-in-CI are the proven 'data-not-code' spine). The panel is collectively high-quality and accurate; its weakness is altitude and priority, not correctness. CORRECT the priority stack: (1) FIRST split tools/trustpager_api.py into a vendor-neutral kernel module + a TrustPager driver module, proven by a no-op second driver — nothing else is real until this boundary exists (biggest risk). (2) Make ONE decision on the dual data surface and declare it per-app: MCP = the journaled/approval-gated WRITE+act surface, pasted key = read-only fan-out speed surface; then fix the 'every write is journaled' promise to MATCH reality (journal MCP writes via a thin post-write helper, or honestly scope the claim) — a live shipping falsehood, not a future risk. (3) Demote the onboarding engine AND its proposed ledgers OUT of the kernel — kernel owns the profile/progress SCHEMA and the registry; the grill, drift-diff, and nudges are apps that read/write those — or the thin-kernel non-negotiable dies in v1. (4) Resolve the plugin-loader open item EMPIRICALLY before any file moves (kernel/ and drivers/ are DATA dirs; triggerable behaviour MUST live in skills/; no ${CLAUDE_PLUGIN_ROOT} or hooks exist in the repo yet). **Overblown:**
- [Extensibility lens] manifest_version + forward-migration engine as 'the single cheapest insurance against core rot' (HIGH). For a markdown-frontmatter contract with a CLOSED schema and CI that regenerates the registry on every push, you do not need a version field on day one. The repo's own analog proves it: lint-skill.py (REQUIRED_FRONTMATTER, line 41) has shipped ~58 skills with no version field and no rot, because the registry is regenerated, not migrated. With ONE source repo and CI failing on unknown keys, a schema change is a global find-replace across N manifests in one PR, not a mixed-vintage problem. manifest_version earns its place only when out-of-tree community PRs land manifests the core team cannot edit in lockstep — a year-2 concern. Adding a migration switchboard now is the speculative core-fattening the mandate warns against.
- [Extensibility lens] requires_driver_version / capability-probe / per-driver capability declarations (e.g. accounting.invoices.read) to absorb non-CRM vendor drift (HIGH + a dedicated optimization + open question). This engineers for 19 drivers that do not exist against a drift problem that mostly is not real yet: the only non-CRM 'driver' that ships (Xero) is reached THROUGH TrustPager's query_integration, so its endpoint drift is absorbed by TrustPager's own catalog/resolve_path, not by BOS. Building a capability-probe abstraction + per-driver override tables before a single independent-MCP driver exists is over-design. The right v1 move is the data-access TYPE taxonomy (which the same lens correctly raises); capability-pinning waits until driver #3 is a genuine Claude-side MCP.
- [Kernel lens] reads_for_profile 'fuses two unrelated buses' and must be split into two generated projections at v1 (MEDIUM). Real, but graded too high vs cost-of-delay. With a registry GENERATOR already in the design, emitting one extra projection is a ~10-line change available any time; carrying both fields in one manifest causes zero runtime harm until the schema actually needs to bump. Flagging it is fine; treating it as design-shaping competes for attention with the genuinely load-bearing splits (shared-lib, dual-surface). Right idea, wrong weight.
- [Migration lens] 'No rollback story — a botched git pull bricks a paying cohort' framed at HIGH as if it stresses the architecture. It is a real operational gap but it is a DISTRIBUTION/release-engineering decision (tag releases, pin INSTALL.md to a tag, or ship via the versioned /plugin path), entirely separable from the kernel/driver/app schematic. You can adopt every architectural decision unchanged and fix this with one INSTALL.md edit. Correct to name; miscategorized as an architecture risk.

**Blind Spots:**
- NOBODY MODELED THE CREDIT/COST FAILURE MODE OF AUTONOMOUS DEEPENING IN A PAID COMMUNITY. The product is Claude autonomously sweeping, drafting, nudging, and 'deepening' — and templates/CLAUDE.md line 31 says voice calls are most expensive, sends/AI-gen cost credits. A member who lets their 'partner' run daily sweeps + reward-loop re-reads + AI drafts can rack up TrustPager credits AND Claude tokens unexpectedly. - NOBODY ASKED WHAT THE KERNEL SAYS TO AN OWNER WHO NEVER CONNECTS THE TRUSTPAGER CRM. Decision 1 (CRM hard-wired TrustPager) collides with decision 2 (owners never hear 'TrustPager is one driver') hardest for exactly the new 'anyone' ICP the pivot chases. The migration lens counts the literals but no lens asks the design question: is the floor genuinely vendor-neutral, or is 'platform-agnostic for anyone' contradicted by a floor that assumes TrustPager?
- NOBODY STRESS-TESTED THE GENERATOR ITSELF AS A NEW ALWAYS-ON FAILURE POINT. - NOBODY NAMED MULTI-MACHINE / STATE-LOCALITY AS ARCHITECTURAL. A Skool member on laptop + desktop has TWO diverging brains and a grill that restarts from zero on machine #2. For a product sold as a persistent 'partner that deepens over years', state being per-machine AND split across two locations (home dir vs project dir) is a structural defect, not an onboarding detail. The kernel has no notion of a portable single-source profile+progress store.
